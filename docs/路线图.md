# 路线图

> 本文是 AgentBridge **唯一**的待办与优先级来源。其它文档只描述现状，不再各自维护 TODO。
>
> 状态图例：**DONE** 已实现并可用 · **PARTIAL** 部分实现 / 有真实缺口 · **TODO** 尚未实现。
>
> 原则：**CLI/Core 是主接口，MCP 是 AI 控制入口，Web 是管理控制面。** 先稳定 Core，再扩展高级能力。

## 一、架构原则

1. CLI / Core 是真正的产品主体，完整能力均可在无 GUI 环境使用。
2. Web 不拥有独立于 Core 的业务逻辑，只是管理与可视化界面。
3. MCP 是 Brain 与本地 AgentBridge 通信的主要入口，只读 + 任务委托。
4. SQLite 保存运行数据与动态配置；`config.toml` 保存启动级配置。
5. Service Lifecycle 与 Executor Process Lifecycle 严格分离。
6. Agent 配置集中于 `~/.agentbridge/.agent`，与工作区解耦。
7. SQLite 是任务 / C2C 权威状态；`handoff/<task_id>.c2c` 只是渲染副本。
8. 高级功能必须建立在稳定的 Core 之上。

## 三、P0 —— 基础稳定性（DONE）

### P0-1 Service Lifecycle —— DONE

- `agentbridge start` / `stop` / `restart` / `status`；`serve` 是唯一前台底层入口。
- 防重复启动、stop 未运行时安全返回、`status` 准确判定。
- 服务 PID 与 Executor PID 分离；生命周期状态存 `service.json`，不依赖 SQLite。
- 误杀防护：健康探针校验归属，必要时 `--force`。
- 为 Windows Service / systemd / launchd 保留 `ServiceBackend` 扩展边界。

### P0-2 Config —— DONE

- `config.toml` 为启动级唯一 Source of Truth，首次启动自动创建。
- 默认 host `127.0.0.1`、`allow_any_host = true`、日志 `info`。
- 修改后通过 `restart` 生效，host/port 不落 SQLite。
- 示例配置补全（文档维护项，非功能缺口）：`examples/config.toml` 已包含与当前 schema 一致的 `[proxy]` 段；端口说明为「调试默认 8040 / 发布默认 8030」。见 [配置](配置.md)。

### P0-3 Core 稳定性 —— DONE

```text
cargo fmt --check
cargo check --all-targets
cargo test
```

以及 `start → status → stop → status → restart → status` 实际运行验证与 MCP 联调。

## 四、P1 —— Web 管理控制面

### P1-1 Web 基础框架 —— PARTIAL

已实现：布局、Sidebar 导航、页面路由、Loading / Error / Empty 状态（`StateView`）、`useAsync`、内置 `ui` 组件、响应式基础。

缺口：无统一的表单体系、Modal / Dialog、Toast / Notification；部分页面仍是占位。见 [Web管理](Web管理.md)。

### P1-2 Dashboard —— PARTIAL

已实现：网关地址/连接客户端、项目、执行器、任务统计、代理状态、项目列表、当前任务选择、活动流；手动刷新。

缺口：

- TODO 真正的任务进度条与 Stage。
- TODO 系统监控（CPU / Memory / Disk）。
- TODO Recent Logs 日志面板。
- PARTIAL 执行器的 `available` / `implemented` 在 Dashboard 快照中为硬编码，应改为探测结果。

### P1-3 Provider / 模型管理 —— PARTIAL

已实现（后端）：

- `providers` / `provider_models` / `provider_credentials` 表与完整 CRUD。
- 凭据 AES-256-GCM 加密存储，API 只回传「已配置」元数据。
- `ProviderRegistry` 解析（默认 Provider / 按名或 id）、单默认约束。
- 管理 API：`/api/providers`、`/credential`、`/models`、`/resolve`。

缺口：

- TODO Web **Provider** 页面（当前占位）。
- TODO **实际模型调用**：`base_url`、凭据、`proxy_id` 目前均为惰性字段，无任何出站 Provider 请求。
- TODO 连接测试（Provider / Model）。
- **Text / Vision / Image 能力配置：TODO**，当前 `kind` 为任意字符串，无能力枚举与校验。

### P1-4 Proxy Manager —— PARTIAL

已实现：`ProxyConfig` / `ProxyView`、单个默认代理的持久化与 patch、连通性测试（`POST /api/proxy/test`）、按 `proxy_id` 解析并注入 Executor 子进程环境。

缺口：

- TODO 多代理管理与专用 **代理** 页面（当前占位）。
- TODO Provider → Proxy 路由（`provider.proxy_id` 未使用）。
- PARTIAL `socks5h` 折叠进 `Socks5`，无独立类型。
- TODO 代理凭据加密（当前 SQLite 明文）。

### P1-5 Executor Manager —— PARTIAL

已实现：登记 / 列表 / 探测可用性 / 测试 / 删除；`Executor` trait + `ExecutorRegistry`；按代理路由。

缺口：

- TODO **Codex / Claude** 适配器（仅白名单登记与探测，不能启动）。
- TODO Web 登记表单目前固定 `opencode`，缺少类型选择与编辑。

### P1-6 Project Manager —— PARTIAL

已实现：`ProjectHub` 多项目、每项目独立 `TaskRuntime`、挂载/列表/删除、active / readonly / executor / 项目类型 / git 状态。

缺口：TODO Web 编辑（更新）项目表单；TODO 项目级配置可视化。

### P1-7 Task Manager / C2C 可视化 —— PARTIAL

已实现：CLI 与 MCP 的 `task_start` / `task_status` / `task_cancel`；`task_records` 按 task_id 权威持久化；每项目单活动任务。

缺口：

- TODO Web **当前任务** 与 **任务历史** 页面（当前占位）。
- TODO 任务 REST：除 `POST /api/projects/{name}/tasks/cancel` 外无启动 / 查询接口。
- TODO Task Detail（iteration、changed files、tests、execution summary、时间线）。

### P1-8 系统设置 —— PARTIAL

已实现：`GET/PUT /api/system/connection` 读写 host/port/no_auth/allow_any_host/认证/executor；Web 设置页展示连接信息与代理开关。

缺口：

- TODO `GET /api/system/settings` 目前返回固定 JSON，应改为读取真实配置 / UI 偏好。
- TODO 启动级设置与 `config.toml` 的一致性校验（Web 不得建立第二套配置来源）。

### P1-9 日志中心 —— TODO

目标：CLI stdout/stderr + 持久化日志 → Web Log Viewer。需支持实时/历史、级别、搜索、过滤、时间、Service / Task / Executor / Error 分类，以及后续 rotation。当前仅有 `service.log` 与 tracing 输出。

## 五、P2 —— 任务体验与安全可视化

### P2-1 Task Execution State / Progress —— TODO

目前只有 Task Status，没有 stage/progress 模型。建议状态：`Queued → Planning → Preparing → Executing → Testing → Reviewing → Completed`；

建议字段：`stage`、`progress`、`message`、`started_at`、`finished_at`、`iteration`。原则：进度必须基于可观察状态，不按执行时间估算。需同步暴露到 CLI、MCP `task_status` 与 Web。

### P2-2 Task History —— PARTIAL

已具备按 task_id 的持久化与索引；TODO 历史查询 API、按时间/项目/执行器/状态筛选、时长、变更文件、测试结果与执行摘要，以及 Web 历史页。

### P2-3 OAuth / Security 管理界面 —— TODO

OAuth 2.1 后端完整（PKCE、动态注册、Admin PIN、限流）。TODO Web **安全 / OAuth** 页面：OAuth 客户端、access/refresh token、认证状态、MCP Auth、Security Status。绝不能在日志或界面回显 Admin PIN / Token / 凭据。

### P2-4 System Monitoring —— TODO

Dashboard 增加 CPU / Memory / Disk / Network / Process / Uptime，用于判断 AgentBridge 健康度；不做复杂监控系统。

## 七、推荐开发顺序

```text
P0 基础稳定性（已完成）
        ↓
P1 Web 控制面补全与 Provider / Proxy / Task 可视化
        ↓
P2 任务进度、历史、OAuth 安全界面、系统监控
        ↓
P3 Agent 深度、Skill 闭环、多用户 / Cloud
```

## 八、开发原则

1. **先稳定，再扩展**：基础设施不稳时不并行开发高级功能。
2. **Core First**：任何能力首先存在于 Core；CLI 是第一控制面，Web 只是第二种操作方式。
3. **不要复制业务逻辑**：`CLI / MCP / Web → Core`，而不是各自一套实现。
4. **配置职责清晰**：`config.toml`（启动级）/ SQLite（运行数据）/ `.agentbridge/.agent`（Agent 上下文）各司其职。
5. **小批次开发**：实现 → 测试 → 实际运行 → 验收 → 下一阶段。
6. **文档不夸大**：未实现能力不得写成已支持（尤其 Codex / Claude Executor、Provider 实际调用、Text/Vision/Image 能力）。
